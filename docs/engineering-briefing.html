Technical briefing · local OAuth2/PKCE SSO stack

How this system works, and how to stand it up

A React SPA, Microsoft Entra ID, and a Spring Boot resource server, wired for the Authorization Code flow with PKCE and run entirely on Docker Desktop. This document is written to be read without further context — architecture, the actual CLI commands, and the behaviors you should expect, including the ones that look like bugs but aren't.

Repo github.com/<owner>/entractive Stack React + MSAL · Spring Boot 3.3 · Entra ID Local ports 3000 (SPA) · 8080 (API) Tests 14, offline
0

What this is

A fully local OAuth2 Authorization Code + PKCE reference implementation. Two containers — a React single-page app and a Spring Boot API — talk to each other over localhost, with Microsoft Entra ID as the only piece that isn't containerized. There is no client secret anywhere in this system; that is the point of PKCE, not an oversight.

Read this top to bottom once if you're setting the system up for the first time. After that, use the left rail — every section stands alone as a reference.

System topology

Three parties, two of which are containers you run and one of which is a cloud identity provider you do not control and cannot emulate locally.

Entra ID is a hard dependency for sign-in — it cannot be run offline, mocked in Docker, or substituted. Everything downstream of a successfully issued token works offline.

The three identities in play

sso-spa
Public client (no secret). Registered under Entra's Single-page application redirect platform specifically — this is what makes PKCE possible instead of a client-secret flow.
sso-resource-server
The API. Exposes one OAuth2 scope (Api.Access) and one app role (Resource.Admin). Tokens are minted for this identity — its client ID is the expected aud claim.
Tenant
The Entra ID directory both app registrations and the signed-in user belong to. One GUID (TENANT_ID) identifies it everywhere.
2

The PKCE flow

PKCE (Proof Key for Code Exchange, RFC 7636) exists because a browser-based app cannot keep a secret — anyone can read the SPA's bundle. Instead of authenticating with a stored secret, the SPA proves it is the same client that started the flow.

Sequence, in order
#StepDetail
1Challenge generatedSPA creates a random code_verifier, hashes it (SHA-256) → code_challenge
2Redirect to Entra IDBrowser navigates to Entra's /authorize endpoint carrying the challenge only — the verifier never leaves the browser at this point
3User authenticatesPassword + MFA, handled entirely by Microsoft — this app never sees credentials
4Redirect backEntra ID sends the browser back to SPA_REDIRECT_URI with a one-time authorization code
5Code exchangeSPA POSTs the code plus the original code_verifier to Entra's /token endpoint
6Verifier checkedEntra hashes the verifier, compares to the challenge from step 1. Match → issues an access token, ID token, refresh token
7Every API callAuthorization: Bearer <access_token> on each request to the resource server
Why

An attacker who intercepts the code in step 4 cannot redeem it — they don't have the verifier, which was never transmitted until step 5, over a direct (non-redirect) connection. A stolen client secret in a traditional confidential-client flow is reusable indefinitely; a stolen authorization code without its verifier is worthless.

Token shapes observed from a real sign-in

These claim shapes were captured off a live token issued by this project's own tenant — they are not invented examples.

access_tokendecoded JWT payload
aud    = api://6841df0b-ee33-4828-8ddf-a017945f9bb5   ← this API's client ID, not the SPA's
iss    = https://sts.windows.net/<tenant>/         ← see §12, defect 2 — two valid issuer shapes exist
scp    = Api.Access
roles  = ["Resource.Admin"]
amr    = ["pwd","mfa"]                             ← authentication methods actually used
Note

The id_token from the same sign-in carries aud = the SPA's client ID — different from the access token's audience. The two tokens are scoped to different consumers and are not interchangeable. The resource server only ever sees the access token.

3

Token validation, server-side

A signature alone is not sufficient. Four independent checks run on every request, implemented in SecurityConfig.java:

CheckRejectsImplementation
SignatureForged or tampered tokensNimbusJwtDecoder against Entra's JWKS, fetched once and cached (no per-request network call — NFR-2)
IssuerTokens from a different tenantTenantIssuerValidator — a custom validator, not Spring's default (see §12)
AudienceA validly-signed token minted for a different APIAudienceValidator — accepts either <client-id> or api://<client-id> spelling
ExpiryReplayed old tokensJwtValidators.createDefault()

The audience check is the one people skip, and it's the one that matters most: without it, any correctly-signed token from your tenant — including one issued to a completely unrelated application — would be accepted. This was verified by deletion: removing AudienceValidator from the decoder chain and re-running the test suite turned a wrong-audience 401 into a 200 (§12 records the full list of mutation tests).

Why the issuer check is custom, not Spring's default

Entra ID mints two different, both legitimate, issuer strings for the same tenant depending on how the client's authority was configured:

v2.0 shape
https://login.microsoftonline.com/<tenant>/v2.0
v1.0 / STS shape
https://sts.windows.net/<tenant>/ — what MSAL's default authority (no explicit /v2.0 suffix) actually produces

Spring's JwtValidators.createDefaultWithIssuer() pins exactly one string. This project hit that mismatch against a real tenant — the fix and its proof are in §12, defect 2.

4

401 vs 403 — read this before filing a bug

The single most common false alarm in this system. The distinction is load-bearing, not cosmetic:

401 Unauthorized
"I don't know who you are." No token, a malformed token, an expired token, a bad signature, wrong issuer, wrong audience. You never got past authentication.
403 Forbidden
"I know exactly who you are. You're not allowed." The token is completely valid — it just doesn't carry the Resource.Admin role. You passed authentication and failed authorization.
EndpointRequiresNo tokenValid token, no roleValid token, with role
GET /api/resourceAny valid token401200200
GET /api/adminValid token + Resource.Admin401403200
Pitfall

Entra ID ships app roles in a roles claim. Spring Security's default authorities converter only reads scope/scp — it never looks at roles at all. Running this project's security config with Spring's stock converter makes /api/admin return 403 for every token, forever, regardless of role assignment. It looks like correct security. It is a silently broken role gate.

This is exactly why SecurityConfig.jwtAuthenticationConverter() exists as a hand-built converter rather than Spring's default — and why it's mutation-tested (§12) rather than merely read and trusted.

CLI command reference

The individual az operations the bootstrap script runs, if you want to run them by hand, adapt them, or understand exactly what's touching your tenant.

A tenant must already exist — the CLI cannot create one

Fact

There is no az command, and no Graph API call, that provisions a new Entra ID tenant. A tenant is created exactly two ways: automatically on a Microsoft account's first sign-in to any Entra service, or manually in the portal (Entra ID → Overview → Manage tenants → Create). az login only resolves to whichever tenant already exists for the signed-in account — it cannot manufacture one.

If az account show returns no tenant at all, every subsequent az ad app command fails, because there's nothing to register into. Sign into entra.microsoft.com once in a browser first if you've never used Entra ID before — that's what provisions it.

Login and identity

az login
# if MFA forces a tenant-scoped login:
az login --tenant <TENANT_ID>

# confirm what you're signed into
az account show --query '{tenant:tenantId, user:user.name}' -o json

# resolve your own object ID (needed for role assignment)
az ad signed-in-user show --query id -o tsv

Confirming you can register apps at all

Before building anything, this is worth running in isolation — it's the fastest way to tell "my account is broken" apart from "my tenant policy blocks this":

az ad app create --display-name "permission-test" --query '{appId:appId, id:id}' -o json
# if it returns an appId, you have the rights you need — delete the probe:
az ad app delete --id <appId from above>

If this errors with "insufficient privileges," that's a tenant-wide setting (Entra ID → Users → User settings → Users can register applications), not a problem with your account. An admin can fix it tenant-wide, or grant you the narrower Application Developer directory role instead.

Finding what already exists (idempotency pattern)

az ad app list --display-name "sso-resource-server" \
  --query "[?displayName=='sso-resource-server'] | [0]" -o json

This is the check-before-create pattern the bootstrap script runs before every write — if this returns a result, reuse its appId/id rather than creating a duplicate.

Creating the app registrations

az ad app create --display-name "sso-resource-server" --sign-in-audience AzureADMyOrg -o json
az ad app create --display-name "sso-spa" --sign-in-audience AzureADMyOrg -o json

az ad app create accepts no flag for app roles, OAuth2 permission scopes, or the SPA redirect platform — those aren't exposed on the plain CLI surface at all. Each needs a raw Graph API call via az rest:

Set the SPA redirect platform (not "Web" — see §13)

az rest --method PATCH \
  --uri "https://graph.microsoft.com/v1.0/applications/<object-id>" \
  --headers "Content-Type=application/json" \
  --body '{"spa": {"redirectUris": ["http://localhost:3000"]}}'

Add the Api.Access scope + Resource.Admin app role

az rest --method PATCH \
  --uri "https://graph.microsoft.com/v1.0/applications/<API object-id>" \
  --headers "Content-Type=application/json" \
  --body @scope-and-role.json
# — see docs/scripts/bootstrap-entra.sh for the exact JSON body this constructs

Service principals, consent, role assignment

# service principals must exist before consent or role assignment can target them
az ad sp create --id <appId>

# tenant-wide admin consent for the delegated scope
az rest --method POST \
  --uri "https://graph.microsoft.com/v1.0/oauth2PermissionGrants" \
  --body '{"clientId": "<SPA sp id>", "consentType": "AllPrincipals", "resourceId": "<API sp id>", "scope": "Api.Access"}'

# assign the app role to a user
az rest --method POST \
  --uri "https://graph.microsoft.com/v1.0/users/<user object-id>/appRoleAssignments" \
  --body '{"principalId": "<user object-id>", "resourceId": "<API sp id>", "appRoleId": "<role id>"}'
Proven

Every command pattern above was run live against this project's own tenant — including a full teardown (az ad app delete on both apps, confirmed gone via az ad app list --query 'length(@)' returning 0) followed by a complete rebuild through the bootstrap script, landing freshly-minted client IDs, and a confirmed working sign-in against the new registrations.

PowerShell equivalents

The PowerShell script (docs/scripts/bootstrap-entra.ps1) runs the identical sequence via ConvertFrom-Json instead of jq. It was hand-reviewed for known Windows-specific failure modes rather than executed:

No param() block
PowerShell requires param() to be a script's literal first statement — which breaks entirely when the script is pasted inline into a terminal rather than saved and run as a file. Uses an environment variable instead, matching the bash version's convention.
BOM-free file writes
Set-Content -Encoding utf8 on Windows PowerShell 5.1 silently emits a UTF-8 byte-order mark, which can break JSON parsing and .env loaders. Every file write uses [System.IO.File]::WriteAllText with an explicit no-BOM encoding instead.
Normalized null handling
Every az ... -o tsv read is wrapped in a helper that treats $null, an empty string, and the literal text "null" as the same "not found" signal, rather than relying on unverified behavior across az/PowerShell version combinations.

If the PowerShell script hits anything unexpected, the bash version under WSL2 or Git Bash is the better-tested fallback — identical outcome, same script either way.

Manual path (Azure portal)

If you'd rather click through the portal than run a script, or need to see exactly what the CLI is automating, the full walkthrough — field-by-field, with the SPA-vs-Web platform trap called out explicitly — lives in docs/entra-id-setup.md in the repo. The short version:

1. API registration
App registrations → New registration, name sso-resource-server, no redirect URI. Then Expose an API (scope Api.Access) and App roles (value Resource.Admin).
2. SPA registration
New registration, name sso-spa, platform Single-page application (not Web — this is the single highest-impact field on the whole form, see §13), redirect http://localhost:3000.
3. Connect + consent
SPA's API permissions → add the API's Api.Access delegated scope → Grant admin consent.
4. Role assignment
Enterprise applications → sso-resource-server → Users and groups → assign yourself Resource Admin.

Bring the stack up

Once .env exists (from §5 or §7):

All platforms — docker invocations are byte-identical

docker compose up --build -d
docker compose ps              # both rows should read (healthy)
docker compose logs -f         # live request-level logs

First build takes roughly two minutes (Maven + npm dependency downloads happen inside the build, not on the host). Subsequent docker compose up reaches healthy in about 11 seconds on prebuilt images — measured on an M1 Max, not the spec's minimum-spec host, so treat that figure as a ballpark with headroom rather than a guarantee.

Note

No JDK, Maven, or Node install is required on the host for any of this — both images build entirely inside Docker.

Ports already taken

If 3000 or 8080 are in use by something else on your machine, set SPA_HOST_PORT/API_HOST_PORT in .env — but Entra ID matches the redirect URI exactly, including the port. Changing the port without updating the registered redirect URI produces AADSTS50011 (§11).

Design

.env is read by the container at startup, not baked into the image at build time. The SPA's nginx entrypoint regenerates a small /config.js from its environment on every container start — so changing .env needs a container restart, never a rebuild, and the same image works across any tenant.

Known defects and fixes

Found by running the system against a real tenant, not by reading the code — each is recorded because a plausible-looking implementation produced an observably wrong result.

1 · Converter bean broke the entire application context

Exposing the JWT authorities converter as a @Bean of type Converter caused Spring MVC's FormattingConversionService to adopt it as a general-purpose type converter, which cannot infer generic types from a lambda. Every test errored at context load.

Fixed by building a concrete JwtAuthenticationConverter instance instead of publishing a lambda-backed bean.

2 · Real tokens rejected with "The iss claim is not valid"

The resource server was hardcoded to accept only the .../v2.0 issuer shape. A real sign-in against this project's actual tenant produced a token with the sts.windows.net/... shape instead — a legitimate alternate issuer Entra ID mints depending on the client's configured authority (see §3). Every authenticated call returned 401 despite a completely valid token.

Fixed with TenantIssuerValidator, which accepts either shape for the configured tenant ID. Mutation-tested: restricting the validator back to v2.0-only was confirmed to reproduce the exact original failure, then reverted.

3 · Frontend threw "text is not defined" on every authenticated call

A refactor of the "render an empty response body legibly" logic was applied to the unauthenticated code path but not the authenticated one, leaving a reference to a variable that only existed in the sibling function's scope. Every "Valid token" and "Role-gated" button click threw a ReferenceError in the browser before the HTTP response was ever read — masking whatever the server actually returned.

Fixed by correcting the body-parsing call; confirmed in a real browser with zero console errors afterward.

4 · NFR-4 request logging produced no output at all

A @Component + @Order(MAX_VALUE) filter is ordered after Spring Security's filter chain, so requests rejected with 401/403 short-circuited before the logging filter ever ran. A stated requirement with zero live code path, which read as satisfied in source.

Fixed with an explicit FilterRegistrationBean at HIGHEST_PRECEDENCE; confirmed by observing 401 lines appear in docker compose logs.

5 · SPA container reported unhealthy while nginx was fine

The healthcheck used localhost, which resolves to ::1 first inside the container — but nginx was configured to listen on IPv4 only. Connection refused on every health probe.

Fixed by pointing the healthcheck at 127.0.0.1 explicitly.

Mutation tests — proving the guards are load-bearing

A passing test suite proves nothing about a specific guard until that guard has been deliberately broken and watched fail. Three guards were mutated, each reverted by reversing the exact edit and diffed byte-identical afterward:

MutationResult
Removed AudienceValidator from the decoder chainwrongAudienceReturns401 → expected 401, got 200
Stopped mapping the roles claim to authoritiescorrectRoleReturns200 → expected 200, got 403
Replaced the CORS origin allowlist with *corsPreflightFromOtherOriginRefused → expected 403, got 200

Design decisions worth knowing

Runtime config, not build-time

Vite resolves import.meta.env at build time, which would bake a specific tenant's IDs into the Docker image — one image per tenant, and secrets-adjacent values frozen into a shippable artifact. Instead, the SPA container's nginx entrypoint writes a small /config.js from its live environment on every container start. One image works across any tenant; changing .env needs only a restart, never a rebuild.

JWKS fetched lazily, not via discovery

Spring's withIssuerLocation() fetches Entra's OpenID discovery document eagerly at startup and aborts the whole application context if that fetch fails. That would make the resource server refuse to boot before the Entra registrations exist, or with no internet — exactly the state a fresh clone starts in. The JWKS URI is instead derived by URL convention from the tenant ID; a genuinely bad tenant then surfaces as a 401 on the first request, not a crash loop at startup.

SPA platform, not Web (repeated because it's the costliest mistake)

Registering the SPA under Entra's Web redirect platform makes Entra expect a client secret on every token redemption. A browser app cannot hold a secret — that's the entire reason PKCE exists. Get this one field wrong and the failure (AADSTS9002326) looks like a CORS problem, not a one-click portal fix.

No client secret, anywhere, by design

Verified directly against the live app registration: az ad app show --id <spa> --query 'length(passwordCredentials)' returns 0. Also verified in the built SPA bundle — grepping the compiled JavaScript for the tenant ID returns zero matches; the only GUID-shaped strings present are MSAL's own hardcoded well-known constants.
